# اعلان در تلگرام + اطلاعات واریز (آدرس کیف پول)

دو قابلیتی که این سند توضیح می‌دهد به هم ربطی ندارند جز اینکه هر دو یک
«شکستِ بی‌صدا» را می‌بندند: چیزی که کار نمی‌کرد ولی خطایی هم نمی‌داد.

---

## ۱. اعلان‌های سایت در تلگرام

### مسئله

`createNotification()` فقط یک ردیف در جدول `notifications` می‌ساخت. یعنی
تأیید فیش واریز، پاسخ تیکت، هشدار پایان تریال و اعلان سراسری — تا وقتی کاربر
خودش سایت را باز نمی‌کرد و روی زنگوله نمی‌زد — به او **نمی‌رسید**. هیچ مسیر
تحویلی به تلگرام وجود نداشت.

### راه‌حل

`api-server/src/lib/notifyTelegram.ts` همان اعلان را از طریق **بات پلتفرم**
(`TELEGRAM_BOT_TOKEN`) به چتِ خود کاربر هم می‌فرستد.

**چرا بات پلتفرم و نه بات پشتیبانی؟** `users.telegramId` دقیقاً از مسیر همین
بات پر می‌شود (`/start <token>` در `lib/registrationBot.ts`، همان باتی که کد
ورود می‌فرستد). تلگرام اجازه نمی‌دهد باتی به کاربری پیام بدهد که قبلاً با آن
بات چت را شروع نکرده باشد — پس این تنها باتی است که برای هر کاربرِ لینک‌شده
یک `chat_id` معتبر و تضمینی دارد. بات پشتیبانی در مخزن جداگانه‌ای است و
`chat_id` کاربران سایت را ندارد.

### نقاطی که وصل شده

| نقطه | فایل | نتیجه |
|---|---|---|
| اعلان تک‌کاربره | `lib/notify.ts` → `createNotification` | همه‌ی call site ها (خرید، کیف پول، تیکت، بات) خودکار پوشش داده شدند |
| اعلان سراسری | `lib/notify.ts` → `createNotificationsBulk` | فقط برای کاربرانی که واقعاً اعلان تازه گرفتند |
| تریال | `lib/trial.ts` → `createNotificationOnce` | فقط وقتی insert موفق بوده (`dedupe_key` تکراری = بدون پیام) |

### قراردادها

- **هرگز throw نمی‌کند.** شکست تحویل فقط `logger.warn` است؛ خریدی که اعلان
  تولید کرده نباید به‌خاطر تلگرام شکست بخورد.
- **fire-and-forget.** `deliverToTelegramInBackground` — پاسخ HTTP منتظر
  رفت‌وبرگشت با تلگرام نمی‌ماند.
- **بدون `TELEGRAM_BOT_TOKEN` بی‌صدا no-op می‌شود** (محیط توسعه کردنشیال
  واقعی ندارد؛ هیچ درخواست شبکه‌ای زده نمی‌شود).
- **ارسال پشت‌سرهم با ۴۰ms فاصله**، نه `Promise.all`: سقف تلگرام برای پیام
  انبوه حدود ۳۰ پیام در ثانیه است و fan-out موازیِ یک اعلان سراسری مستقیم به
  429 می‌خورد.
- کاربرِ بدون `telegram_id` یا با `notify_telegram = false` کنار گذاشته
  می‌شود؛ اعلانِ **سایتش** دست‌نخورده می‌ماند.

### کنترل کاربر

ستون `users.notify_telegram` (پیش‌فرض `true`). سوئیچش در **پروفایل → کارت
تلگرام** است و فقط وقتی تلگرام وصل باشد دیده می‌شود
(`components/profile/TelegramNotifyToggle.tsx`).

| متد | مسیر |
|---|---|
| `GET` | `/api/users/notification-prefs` → `{ notifyTelegram, telegramLinked }` |
| `PATCH` | `/api/users/notification-prefs` با `{ notifyTelegram: boolean }` |

### شکل پیام

```
✅ <b>عنوان اعلان</b>

متن اعلان
[ دکمه: مشاهده در سایت ]
```

آیکن از روی نتیجه‌ی رویداد انتخاب می‌شود (`_approved` → ✅، `_rejected` →
❌، critical → 🚨 …). عنوان و متن با `escape` وارد HTML می‌شوند، وگرنه یک
`<` رهاشده در متنِ نوشته‌ی ادمین کل پیام را از طرف تلگرام رد می‌کند.

دکمه‌ی «مشاهده در سایت» فقط وقتی اضافه می‌شود که `PUBLIC_SITE_URL` تنظیم
باشد، و مقصدش بر اساس نوع اعلان انتخاب می‌شود (`deepLink`). نوع ناشناخته به
`/notifications` می‌رود — هیچ‌وقت لینک شکسته ساخته نمی‌شود.

## ۲. «پول را کجا بفرستم؟» — اطلاعات واریز

### مسئله

تب USDT در صفحه‌ی کیف پول از کاربر «هش تراکنش» می‌خواست ولی **هیچ‌جا آدرس
مقصد را نشان نمی‌داد**؛ یعنی واریز تتر عملاً غیرقابل انجام بود. کارت‌به‌کارت
هم همین‌طور: فیش می‌خواست بدون اینکه بگوید به کدام کارت.

ریشه‌اش این بود که سایت هیچ جدولی برای تنظیمات سطح پلتفرم نداشت.

### راه‌حل

جدول `platform_settings` (کلید/مقدار) + کلید `payment_methods`.

```
lib/db/src/schema/platformSettings.ts   ← تعریف جدول
api-server/src/lib/platformSettings.ts  ← خواندن/نوشتن با پیش‌فرض از env
```

سه لایه‌ی مقدار، به همین ترتیب:

1. ردیف دیتابیس (چیزی که سوپرادمین در پنل وارد کرده)
2. متغیر محیطی — تا قبل از اولین ورود در پنل هم سایت قابل استفاده باشد
3. رشته‌ی خالی → فرانت صریح می‌گوید «این روش هنوز تنظیم نشده»، به‌جای نمایش
   یک کادر خالی

### کجا وارد می‌شود

**پنل ادمین → تب پرداخت‌ها → کارت «اطلاعات واریز»**
(`components/admin/PaymentMethodsSettings.tsx`، فقط سوپرادمین).

فیلدها: آدرس کیف پول، شبکه (TRC20/ERC20/…)، Memo/Tag، نرخ هر تتر به تومان،
توضیح، و سوئیچ فعال/غیرفعال — و برای کارت: شماره، نام صاحب کارت، بانک،
توضیح، سوئیچ.

### کجا دیده می‌شود

**صفحه‌ی کیف پول → تب‌های «کارت» و «USDT»** — بالای فرم، با دکمه‌ی کپی.
شبکه با هشدار نمایش داده می‌شود (ارسال روی شبکه‌ی اشتباه = پولِ برنگشتنی).

روشی که سوپرادمین خاموش کرده، تبش غیرفعال می‌شود **و** سرور هم مستقل از
فرانت درخواستش را رد می‌کند — تصمیم فقط سمت کلاینت گرفته نمی‌شود.

### API

| متد | مسیر | دسترسی |
|---|---|---|
| `GET` | `/api/wallet/deposit-info` | هر کاربر لاگین‌شده |
| `GET` | `/api/admin/payment-settings` | سوپرادمین |
| `PUT` | `/api/admin/payment-settings` | سوپرادمین |

`deposit-info` عمداً پشت `requireAuth` است: شماره کارت مقصد چیزی نیست که روی
اینترنتِ باز بگذاریم.

> ⚠️ `platform_settings` جای **راز** نیست. هرچه در آن باشد ممکن است به کلاینت
> فرستاده شود؛ توکن و کلید همچنان فقط در env می‌مانند.

## متغیرهای محیطی

هیچ‌کدام اجباری نیستند. اگر نباشند، قابلیت بی‌صدا خاموش می‌ماند.

| متغیر | سرویس | نقش |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | irforge-web | **از قبل لازم بود** (ورود با تلگرام). حالا کانال تحویل اعلان هم هست. بدون آن، اعلان‌ها فقط در سایت می‌مانند. |
| `PUBLIC_SITE_URL` | irforge-web | **از قبل لازم بود** (وبهوک). حالا مقصد دکمه‌ی «مشاهده در سایت» هم هست. بدون آن، پیام بدون دکمه فرستاده می‌شود. |
| `USDT_DEPOSIT_ADDRESS` | irforge-web | پیش‌فرض آدرس تتر، تا قبل از اولین ذخیره در پنل. |
| `USDT_DEPOSIT_NETWORK` | irforge-web | پیش‌فرض شبکه. اگر نباشد `TRC20`. |
| `USDT_DEPOSIT_MEMO` | irforge-web | فقط برای شبکه‌هایی که memo/tag لازم دارند. |
| `USDT_TOMAN_RATE` | irforge-web | نرخ هر تتر به تومان. صفر/خالی = نمایش نده. |
| `CARD_DEPOSIT_NUMBER` | irforge-web | پیش‌فرض شماره کارت. |
| `CARD_DEPOSIT_HOLDER` | irforge-web | پیش‌فرض نام صاحب کارت. |
| `CARD_DEPOSIT_BANK` | irforge-web | پیش‌فرض نام بانک. |

**توصیه:** مقادیر واریز را به‌جای env، از پنل ادمین وارد کنید — تغییرشان
دیپلوی نمی‌خواهد. env فقط برای این است که سایت قبل از اولین ورود هم خالی
نباشد.
