# کارت‌به‌کارتِ خودکار (تأیید با پیامکِ بانک) — معماری، راه‌اندازی و عیب‌یابی

> IRFORGE_CARD_AUTOCONFIRM_PROMPT — فازهای ۰–۹. این سند مرجعِ نهاییِ ماژول است. آموزشِ تصویری برایِ کاربرِ نهایی/ادمین: صفحه‌یِ `/tutorials/cardpay` در خودِ سایت
> (`irforge/src/lib/tutorials/cardpayTutorial.ts` + `irforge/public/tutorials/cardpay/`).
> تاریخچه‌یِ تصمیم‌ها فاز‌به‌فاز در `PROGRESS.md` است؛ کشفیاتِ فازِ ۰ در `docs/card_autoconfirm_recon.md`.

## ۱. ماژول چه کار می‌کند

مشتری مبلغ را انتخاب می‌کند، سیستم یک **مبلغِ یکتا** (`مبلغِ درخواستی + چند ریالِ تصادفی`) و شماره‌کارتِ مقصد را نشان می‌دهد؛ مشتری همان مبلغِ دقیق را واریز می‌کند؛ گوشیِ صاحبِ کارت پیامکِ بانک را (با MacroDroid) به وبهوکِ همان کانال می‌فرستد؛ سیستم پیامک را می‌خواند، با درخواستِ بازِ همان کانال **دقیقاً** تطبیق می‌دهد و پرداخت را تأیید می‌کند. اگر تطبیقِ خودکار نشد: فیش + تأییدِ دستیِ ادمین (مسیرِ جایگزین). پول همیشه مستقیم به کارتِ صاحبِ کانال می‌رود؛ **هیچ‌جا CVV2، رمزِ دوم یا OTP گرفته نمی‌شود.**

دو «حوزه» (`scope`) از یک ماژول استفاده می‌کنند:

| حوزه | صاحبِ کانال | چه چیزی شارژ می‌شود | اثرِ تأیید |
|---|---|---|---|
| `platform` | سوپرادمین/خودِ سایت | کیف‌پولِ کاربرِ IrForge | در **همان تراکنشِ تأیید**، کیف‌پول شارژ می‌شود (`platformWalletEffect.ts`؛ نوعِ ledger: `deposit_card_auto`؛ مبلغِ اعتبار = `base_amount_rial`، نه مبلغِ نهایی) |
| `bot` | فروشنده (هر بات) | کیف‌پول/سفارشِ مشتریِ آن فروشنده | سایت فقط وضعیت را تأیید می‌کند؛ بات با پروتکلِ claim (`claimed → done`) اثر را در خودش اعمال می‌کند |

## ۲. معماری

```
گوشی (MacroDroid) ── POST + X-Sms-Secret ──► /api/payments/sms/:channelId      (routes/paymentSmsWebhook.ts)
                                               │ احرازِ کلید (هش)، فرستنده‌یِ مجاز، rate-limit
                                               ▼
                             smsIngest (idempotent با content_hash) ─► sms_inbox
                                               ▼
                       paymentMatcher (قفلِ کانال، مبلغِ دقیق، فقط واریز) ─► confirmRequestTx
                                               ▼                               │ (در همان tx)
                                  payment_requests: confirmed ◄────────────────┘ effect registry
                                               ▼
                    پس از commit: paymentAlerts (اعلان‌ها) + payment_events (لاگ) + ارتقایِ صف
```

فایل‌هایِ اصلی (`api-server/src`):

| فایل | نقش |
|---|---|
| `lib/paymentRequests.ts` | ساختِ درخواست، تخصیصِ مبلغِ یکتا، صفِ رزرو، انقضا (`expireDueRequests`) |
| `lib/smsIngest.ts`, `lib/smsParsers/*` | ورودِ idempotentِ پیامک و پارسرِ بانک‌ها (Blubank …) |
| `lib/paymentMatcher.ts`, `lib/paymentConfirm.ts` | تطبیق + `confirmRequestTx` (تنها راهِ رسیدن به `confirmed`) |
| `lib/paymentEffects.ts`, `lib/paymentEffectsBoot.ts` | رجیستریِ اثر به‌ازای `(scope, purpose)`؛ اثرِ ثبت‌نشده = fail-closed |
| `lib/platformWallet.ts`, `lib/platformWalletEffect.ts` | شارژِ کیف‌پولِ پلتفرم (فاز ۸) |
| `lib/paymentChannelAdmin.ts` | مدیریتِ کانال (ساخت/ویرایش/چرخشِ کلید/تستِ پیامک) — برایِ هر دو حوزه |
| `lib/paymentDecisions.ts` | تأیید/ردِ دستی («اولین تصمیم برنده است») |
| `lib/paymentSweeper.ts` | جاروبِ هر دقیقه (فاز ۹) |
| `lib/paymentEvents.ts` | لاگِ رویدادِ سوپرادمین (فاز ۹) |
| `lib/paymentAdmin.ts`, `routes/adminCardAutoConfirm.ts` | API پنلِ مدیریت (فاز ۸/۹) |

جدول‌ها: `payment_channels`, `payment_requests`, `sms_inbox`, `payment_events` (مایگریشن‌هایِ `0038`–`0041`؛ هم در `api-server/migrate.mjs` و هم آینه‌یِ `lib/db/migrations/*.sql`؛ تستِ schema یکسان بودنشان را قفل می‌کند).

### ترتیبِ قفل‌ها (برایِ جلوگیریِ deadlock)

۱) قفلِ advisory **به‌ازای کانال** (`withChannelLock`) ← ۲) قفلِ ردیف. ساختِ درخواست ابتدا قفلِ کاربر (`withUserLock`) را می‌گیرد؛ ساختِ کانال قفلِ مالک را. تصمیم‌ها همه «`UPDATE … WHERE status IN (باز)`»ِ شرطی‌اند: **اولین تصمیم برنده است**، دومی `decided:false` می‌گیرد.

## ۴. متغیرهایِ محیطی و استقرار

| متغیر | کجا | توضیح |
|---|---|---|
| `DATABASE_URL` | سایت | Postgres؛ مایگریشن‌ها در بوت اجرا می‌شوند |
| `BOT_TOKEN_ENCRYPTION_KEY` | سایت | کلیدِ رمزنگاریِ شماره‌کارت‌ها (همان کلیدِ توکنِ بات‌ها) |
| `PAYMENT_INTERNAL_SECRET` | **هم سایت هم سرویسِ بات اصلی** | احرازِ APIِ داخلیِ بات↔سایت (`/internal/payments/*`). اگر روی یکی نباشد، فروشنده‌ها پرداختِ خودکار ندارند |
| `PUBLIC_SITE_URL` | سایت | پایه‌یِ آدرسِ وبهوکی که نمایش داده می‌شود (مثلاً `https://irforge.ir`). بدون آن، پنل هشدارِ «آدرس عمومی تنظیم نشده» می‌دهد |
| `PAYMENT_REQUEST_EXPIRY_MINUTES` | سایت (اختیاری) | مهلتِ پرداختِ پیش‌فرضِ درخواست‌هایِ تازه، عددِ صحیحِ ۵..۲۴۰ (پیش‌فرض ۳۰). نامعتبر → ۳۰. روی درخواست‌هایِ بازِ فعلی اثر ندارد |
| `BLUBANK_TOPUP_LINK` | سایت (اختیاری) | فقط برایِ مهاجرت: لینکِ مبلغ‌بازِ قدیمی اگر در تنظیماتِ سایت نبود (پیش‌فرض `https://blubiz.sb24.ir/s/skCuUhkl`) |
| `SMS_WEBHOOK_SECRET` | سایت (**منسوخ**) | فقط برایِ alias آدرسِ قدیمیِ وبهوک. وقتی گوشی را به آدرس و کلیدِ جدید بردید، **حذفش کنید** |

استقرار:
1. کد را deploy کنید؛ در بوت مایگریشن‌ها + مهاجرتِ شارژِ قدیمی (idempotent) + شروعِ sweeper خودکار انجام می‌شود.
2. `PAYMENT_INTERNAL_SECRET` را روی هر دو سرویس بگذارید و `PUBLIC_SITE_URL` را تنظیم کنید.
3. پنلِ مدیریت ← «کارت‌به‌کارت خودکار» ← «نمایِ کلی»؛ چک‌لیستِ «راه‌اندازی برایِ خودِ سایت» را کامل کنید (بخشِ ۶).

## ۵. راه‌اندازیِ گوشی (MacroDroid)

هر کانال یک URL و یک کلیدِ امنیتیِ مخصوصِ خودش دارد (کلید فقط یک‌بار موقعِ ساخت/چرخش نشان داده می‌شود). راهنمای تصویریِ کامل: `/tutorials/cardpay` (بخشِ ۳). خلاصه:

1. **گوشی:** اندروید، همیشه روشن و شارژ، اینترنتِ پایدار، سیم‌کارتی که پیامکِ بانکِ همان کارت را می‌گیرد. MacroDroid (رایگان: ۵ ماکرو؛ به‌ازایِ هر کانال یک ماکرو).
2. **مجوزها:** «دریافت/خواندنِ پیامک»، اجرا در پس‌زمینه، Battery = Unrestricted، Auto-start روشن، و خارج بودن از فهرستِ «Sleeping apps» (سامسونگ/شیائومی/هوآوی).
3. **Trigger:** `SMS → Received SMS`، Sender = نامِ دقیقِ فرستنده‌یِ بانک (همان که در «فرستنده‌هایِ مجازِ» کانال هم هست)، Content خالی. *فقط* بانک — پیامک‌هایِ شخصی/OTPِ دیگران نباید از گوشی خارج شوند.
4. **Action (پیشنهادی — text/plain):** `HTTP Request` — Method `POST`، URL = آدرسِ وبهوکِ کانال، Content-Type `text/plain`، Header `X-Sms-Secret: <کلیدِ کانال>`، Header `X-Sms-Sender: <نامِ بانک>`، Body = فقط Magic Text «SMS Message» (`{sms_message}`) و هیچ چیزِ دیگر.
5. **Action (جایگزین — JSON):** Content-Type `application/json`، Body `{"text":"{sms_message}","sender":"Blubank"}`. فیلدِ `time` اختیاری است (ISO یا epoch؛ نباشد، زمانِ رسیدن گذاشته می‌شود).
6. **تست:** «ارسالِ پیامکِ آزمایشی» در پنل (فقط سمتِ سرور) + یک واریزِ کوچکِ واقعی؛ «آخرین پیامکِ دریافتی» باید تازه شود.

**چرا text/plain پیشنهاد می‌شود؟** پیامکِ بانک چندخطی است (`بلو⏎واریز پول⏎…⏎۲۱:۱۱⏎۱۴۰۵.۰۷.۰۷`) و MacroDroid خط‌جدیدها را در بدنه escape نمی‌کند. سرور (`lib/smsBody.ts`) JSONِ دارایِ خط‌جدیدِ خام را ترمیم می‌کند (فقط همین یک عیب)، ولی JSONِ دارایِ `"` بی‌escape داخلِ متن قابل‌ترمیم نیست ← `400 bad_body`؛ text/plain این خطر را ندارد. برایِ همین `app.ts` parserِ سراسریِ JSON را روی این دو آدرس رد می‌کند و خودِ route بدنه را می‌خواند (بدنه ≤ ۱۶KB).

**فرستنده و زمان:** در JSON از `sender|from|address|number` و `time|timestamp|received_at|date` (ISO یا epoch ثانیه/میلی‌ثانیه)؛ در text/plain از هدرِ `X-Sms-Sender`/`X-Sms-Time` یا query `?sender=`/`?time=` (اولویت: بدنه ← هدر ← query). با allowlistِ فعال، پیامکِ بدونِ فرستنده «نادیده» می‌شود.

پاسخ‌هایِ وبهوک: `201` ذخیره شد (`matched:true` = تأییدِ خودکار)، `200` تکراری (بی‌اثر؛ retry امن است)، `400` بدونِ متن یا بدنه‌یِ نامعتبر (`bad_body`)، `401` کلیدِ اشتباه **یا کانالِ ناموجود** (عمداً یکسان تا شناسه‌هایِ کانال قابل‌حدس‌زدن نباشند)، `403` کانالِ غیرفعال، `429` rate-limit (۳۰ درخواست/دقیقه به‌ازایِ IP و ۱۲۰ به‌ازایِ کانال).

**گوشیِ گم‌شده:** «چرخشِ کلید» یا غیرفعال‌کردنِ اضطراریِ کانال. یادآوری: امنیتِ وبهوک همین کلید است؛ کسی که کلید را داشته باشد می‌تواند پیامکِ جعلی بفرستد، ولی فقط پیامکی با مبلغِ *دقیقاً برابر* با یک درخواستِ بازِ همان کانال اثر دارد.

## ۶. کارِ روزمره برایِ سایتِ خودتان

1. پنلِ مدیریت ← «کارت‌به‌کارت خودکار» ← «کانال‌هایِ سایت» ← کانالِ جدید (نوعِ «شماره‌کارت (مبلغِ یکتا)» یا «لینکِ مبلغ‌باز»). حداکثر ۵ کانال.
2. کلیدِ امنیتی را همان لحظه در MacroDroid بگذارید. گم شد → «چرخشِ کلید» (کلیدِ قبلی همان لحظه باطل).
3. پیامکِ آزمایشی + واریزِ کوچکِ واقعی؛ در «نمایِ کلی» چک‌لیستِ پنج‌قدمی باید همه سبز شود.
4. اگر قبلاً گوشی به `/internal/wallet-topup/sms-webhook` وصل بود: تا عوض نکنید همان کار می‌کند (alias). بعد از عوض کردن، `SMS_WEBHOOK_SECRET` را از env حذف کنید.
5. روزانه «نیازمندِ توجه» را نگاه کنید: فیشِ بیش از ۶ ساعت منتظر، اثرِ گیرکرده، پیامکِ مبهم، واریزِ بدونِ درخواست، کانالِ فعال با گوشیِ ساکت، خطا در لاگ.

### شارژِ کیف‌پولِ کاربر (فاز ۸)

`GET /api/wallet/topup/config` (فعال بودن، مبلغ‌هایِ آماده، حداقل)، `GET /api/wallet/topup` (درخواستِ باز)، `POST /api/wallet/topup/request` ‏`{amountToman}`، `POST …/:id/receipt` ‏(data-URL webp/png/jpeg، ≤ ۱۹۰k کاراکتر)، `POST …/:id/cancel`، `GET …/:id/status`.
مبلغ‌هایِ آماده: ۱۰۰/۲۰۰/۵۰۰/۷۰۰ هزار و ۱ میلیون تومان، یا دلخواه (حداقل ۱۰۰ هزار، سقفِ ۵۰ میلیون تومان). درخواستِ هم‌مبلغِ باز → همان برمی‌گردد (idempotent)؛ حداکثر ۳ درخواستِ باز به‌ازایِ هر کاربر؛ مهلتِ پرداخت پیش‌فرض ۳۰ دقیقه (`PAYMENT_REQUEST_EXPIRY_MINUTES`) و صفِ رزرو حداکثر ۱ ساعت. **بعد از ارسالِ فیش** ۵ دقیقه شمارشگرِ «در حال بررسیِ خودکار» نشان داده می‌شود (پیامک در این مدت هنوز تأیید می‌کند)، بعد پیامِ «در حال بررسیِ دستی است» (همان رفتارِ بات؛ `irforge/src/lib/topupCountdown.ts`).
اعتبارِ کیف‌پول همیشه `base_amount_rial` است؛ پسوندِ ریالی فقط برایِ شناساییِ پرداخت است.

## ۷. مهاجرتِ شارژِ قدیمی (`wallet_topups` / `sms_logs`)

هدف: شارژهایِ قدیمی را به مدلِ جدید ببریم **بدونِ ازدست‌رفتنِ اعتبارِ هیچ کاربر و بدونِ ساختنِ اعتبارِ تازه**.

- خودکار در بوتِ سرور اجرا می‌شود و دستی هم قابل‌اجراست (از پوشه‌یِ `api-server`):
  `DATABASE_URL=… node --import tsx/esm scripts/migrateWalletTopups.mjs [--dry-run] [--report گزارش.md] [--json]`
  کدِ خروج: `0` = کامل و بدونِ یتیم، `1` = ناقص/یتیم، `2` = خطا. از پنل هم می‌شود (نمایِ کلی ← «مهاجرتِ شارژِ قدیمی»، dry-run یا واقعی).
- **Idempotent** با ستونِ `legacy_ref` (یکتا)؛ اجرایِ دوباره چیزی نمی‌سازد. یک تراکنش + قفلِ advisory؛ `--dry-run` گزارشِ واقعی می‌دهد و rollback می‌کند.
- نگاشتِ وضعیت‌ها: `pending` → `pending` (مهلت‌گذشته → `expired`؛ دارایِ فیش → `awaiting_review`؛ برخوردِ مبلغ در کانال → `expired`)، `confirmed` → `confirmed` (`confirmed_by='admin'` با شناسه‌یِ `legacy-manual-confirm` یا `sms` اگر پیامکِ وصل‌شده داشت)، `canceled`/`expired` همان‌ها. پسوندِ غیرمضربِ ۱۰ با قیدِ معافِ `legacy_ref` نگه داشته می‌شود.
- **هرگز کیف‌پول را دست نمی‌زند.** گزارش «تأییدشده‌هایِ قدیمی که در ledger ردیفِ شارژ ندارند» را فهرست می‌کند تا **دستی** بررسی شوند.
- گزارش شاملِ: کانالِ platform (از `payment_methods.blubank`؛ فعال/لینک)، شمارِ درخواست‌ها به تفکیکِ وضعیت، پیامک‌ها، تطبیقِ ledger، ردیف‌هایِ یتیم (باید صفر باشد) و «نیازمندِ توجه». نمونه: `docs/card_autoconfirm_migration_report_example.md`.
- معیارِ پذیرش: شارژِ کیف‌پول end-to-end روی ماژولِ جدید، ردیفِ یتیمِ صفر، گزارش تولید شده.

### مسیرِ قدیمی حذف شد (دو مسیرِ موازی وجود ندارد)

حذف‌شده: `walletTopupService.ts`، endpointهایِ ادمینِ قدیمیِ `wallet/topup/*`، `WalletTopupMonitor`، بخشِ Blubank در «روش‌هایِ پرداخت» (اکنون اشاره‌گر به تبِ جدید) و `expireStaleTopups` (جایگزین: sweeper). جدول‌هایِ قدیمی دست‌نخورده می‌مانند (فقط خوانده می‌شوند) تا برگشت/ممیزی ممکن باشد.
آدرسِ `/internal/wallet-topup/sms-webhook` فقط یک alias نازک است (با `SMS_WEBHOOK_SECRET`؛ `503` اگر کانالِ platformِ فعال نباشد) و هر استفاده را با رویدادِ `legacy_webhook_used` ثبت می‌کند.

## ۸. Sweeper (هر دقیقه)

`lib/paymentSweeper.ts` — تک‌اجرایی با قفلِ advisory سطحِ session (چند نمونه‌یِ سرور امن است؛ همه‌ی مراحل idempotent). خطایِ یک مرحله مرحله‌هایِ بعد را متوقف نمی‌کند.

| مرحله | رفتار |
|---|---|
| انقضا | `pending`/`queued`ِ سررسیدشده → `expired` و ارتقایِ نفرِ بعدیِ صف |
| پاکسازیِ پیامک | پیامک‌هایِ `ignored` قدیمی‌تر از **۳۰ روز** حذف (فرستنده‌یِ غیرمجاز/برداشت؛ هرگز match نمی‌شوند) |
| پاکسازیِ لاگ | رویدادهایِ قدیمی‌تر از **۹۰ روز** |
| فیشِ بی‌جواب | `awaiting_review` بیش از **۶ ساعت** → هشدار (یک‌بار به‌ازایِ هر درخواست)؛ عمداً خودکار منقضی نمی‌شود چون پولِ احتمالاً واریز شده |
| گوشیِ ساکت | کانالِ فعال با درخواستِ اخیر ولی بدونِ پیامکِ معتبر بیش از **۱۲ ساعت** → هشدار به سوپرادمین/صاحبِ بات (حداکثر هر ۱۲ ساعت) |
| اثرِ گیرکرده | claimِ بات بیش از **۱۵ دقیقه** بدونِ `done` → هشدار؛ **هرگز خودکار retry نمی‌شود** (خطرِ اعمالِ دوباره‌یِ اثرِ مالی) |

«اجرایِ فوری» در پنل و `POST /api/admin/card-autoconfirm/sweep` همین را اجرا می‌کند؛ آخرین گزارش در «نمایِ کلی» است.

## ۹. لاگِ سوپرادمین (`payment_events`)

هر رویدادِ مهم (ساختِ درخواست، تأیید با پیامک/ادمین، انقضا، رد، لغو، فیش، پیامکِ مبهم/بدونِ کاندیدا، خطای احراز، ساخت/چرخش/تغییرِ کانال، ارتقایِ صف، هشدارهایِ sweeper، خطایِ اثر…) با `level` (`info/warn/error`)، `kind`، حوزه، بات، کانال، درخواست، پیامک و `actor` ثبت می‌شود.
قواعد: **best-effort** (هرگز داخلِ تراکنشِ مالی و هرگز throw نمی‌کند)؛ شماره‌کارت‌ها ماسک (`6037-****-****-1234`)؛ **متنِ کاملِ پیامک هیچ‌وقت ذخیره نمی‌شود**؛ خطایِ احرازِ وبهوک برایِ هر IP throttle می‌شود تا لاگ پر نشود. نگهداری ۹۰ روز. تغییراتِ ادمین علاوه بر آن در `admin_audit_log` هم ثبت می‌شوند (`card_autoconfirm_decision | _channel_active | _sms_assigned | _sweep | _migration`).

## ۱۰. APIِ پنلِ مدیریت (فقط سوپرادمین، `/api/admin/card-autoconfirm`)

`GET overview` · `GET channels` · `POST channels/:id/active` · `GET|POST platform-channels`, `PATCH|DELETE platform-channels/:id`, `POST …/rotate-secret`, `POST …/test-sms`, `GET …/sms-log` · `GET requests`, `GET requests/:id`, `GET requests/:id/receipt`, `POST requests/:id/decide` · `GET sms`, `POST sms/:id/assign` · `GET events` · `POST sweep` · `POST migration/run`.
نوشتن‌ها: rate-limited، در حالتِ impersonation مسدود، و audit شده. `assign` فقط وقتی کار می‌کند که مبلغ دقیقاً برابر و همان کانال باشد و درخواست `pending` یا `awaiting_review` باشد (منقضی/رد/لغو‌شده → `wrong_state`)؛ اثر (شارژ) در همان تراکنش اعمال می‌شود.

## ۱۲. عیب‌یابی

| نشانه | علتِ محتمل | اقدام |
|---|---|---|
| کاربر واریز کرد، تأیید نشد | پیامک نرسید، یا مبلغ با مبلغِ نهایی فرق دارد، یا درخواست منقضی شد | «صندوقِ پیامک» را ببینید؛ درخواستِ بازِ هم‌مبلغ ← «اتصالِ دستی» یا تأییدِ فیش؛ درخواستِ منقضی ← کاربر درخواستِ تازه + فیش بفرستد و شما پس از مقایسه با پیامکِ صندوق دستی تأیید کنید |
| «گوشی ساکت» / «هنوز پیامکی نیامده» | باتری MacroDroid را کشته، اینترنت قطع، ماکرو خاموش | شش موردِ بخشِ ۵ را چک کنید؛ پیامکِ آزمایشی + واریزِ کوچک |
| `401` در لاگِ احراز | کلیدِ X-Sms-Secret اشتباه (بعد از چرخشِ کلید) | کلیدِ تازه را در ماکرو بگذارید |
| پیامک «نادیده» | فرستنده در «فرستنده‌هایِ مجاز» نیست، یا پیامکِ برداشت/تبلیغ | نامِ فرستنده را دقیقاً مطابقِ گوشی تنظیم کنید |
| پیامکِ «مبهم» | دو درخواست با یک مبلغ (تقریباً غیرممکن) | از «اتصالِ دستی» درخواستِ درست را انتخاب کنید |
| «اثرِ گیرکرده» | بات claim کرد ولی `done` نزد | لاگِ درخواست را ببینید؛ retry خودکار نداریم؛ پس از بررسیِ دستی موجودی را اصلاح کنید |
| هشدارِ «آدرسِ قدیمیِ وبهوک روشن است» | `SMS_WEBHOOK_SECRET` هنوز ست است | گوشی را روی آدرسِ جدید ببرید و env را حذف کنید |
| `503` از alias قدیمی | کانالِ platformِ فعالی نیست | کانال بسازید/فعال کنید |
| تب «افزایش موجودی» خاموش | کانالِ platformِ فعال وجود ندارد | در «کانال‌هایِ سایت» یک کانال بسازید و فعال کنید |

برگشت (rollback): کانال را غیرفعال کنید (تب «همه‌یِ کانال‌ها» ← خاموش/روشنِ اضطراری)؛ پیامک‌ها رد می‌شوند و کاربرِ تازه کانال را نمی‌بیند. مایگریشن‌ها فقط ستون/جدولِ جدید اضافه می‌کنند (چیزی حذف نمی‌شود) و جدول‌هایِ قدیمی دست‌نخورده‌اند.
